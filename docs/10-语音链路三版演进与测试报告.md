## 0. 一句话总结

语音作答经历了三代：

| 版本 | 形态 | 出字时机 | 关键问题 |
|---|---|---|---|
| **v1** | 整段录音 → 上传 → 一次性转写 | 停止录音后 11~12s | 交互「像发语音消息」，不像对话 |
| **v2** | WS 长连接 + 100ms 分片 + 服务端 VAD | 说完一句约 1s | 小声漏检、句子切碎、尾句丢失、乱序 |
| **v3** | 同 v2 + 迟滞/自适应/保序/收尾语义 | 说完一句 0.26~0.85s | 噪声环境与方言仍待优化 |

## 1. 版本一：整段录音上传转写

### 1.1 设计

```
浏览器 MediaRecorder 录音（webm/opus）
   ↓ 点击「停止录音并转写」
Blob → POST /api/v1/voice/transcribe（multipart/form-data）
   ↓
VoiceController 落盘 → AsrClient.transcribe(Path)
   ↓ OpenAI 兼容 POST /audio/transcriptions
返回 {text, model, provider, latencyMs, audioPath}
   ↓
前端把 text 填进作答框，用户可编辑后提交
```

要点：

- 录制与转写**串行**，转写期间按钮 loading；
- 结果可编辑，避免识别错误直接影响评分；
- 转写失败不阻塞作答，直接退回文字输入；
- 音频落盘保存（`data/uploads/voice/yyyy/MM/dd/*.webm`），便于后续排查。

### 1.2 实现细节

`OpenAiAsrClient` 负责调用 `POST /audio/transcriptions`，字段 `file` / `model` / `language` / `response_format=json`。

### 1.3 优点

| 优点 | 说明 |
|---|---|
| 实现简单 | 一个 multipart 接口，前端一个 Blob 上传 |
| 容错好 | 失败只需重传，不涉及连接状态 |
| 音频完整 | 整段送 ASR，上下文完整，识别准确率高 |
| 无状态 | 服务端不保存会话，天然支持多实例 |

### 1.4 缺点

| 缺点 | 实测 |
|---|---|
| **延迟高** | 10s 音频从点击停止到出字 **11.5~12.4s** |
| 交互断裂 | 用户必须「先说完 → 再点停止 → 再等」 |
| 无法边看边改 | 转写完成前看不到任何文字 |
| 长答案风险 | 超过 10MB 或 180s 超时要重录 |

### 1.5 当时发现的问题：chunked 上传被 ASR 服务拒绝

**现象**：上传后返回 `503 语音转写失败：500 Internal Server Error: [no body]`。

**定位过程**：

1. 用 `curl -F file=@tmp-voice.wav` 直连 SiliconFlow → **200 成功**，排除文件与 Key 问题；
2. 写 `AsrCaptureTest`，让 `OpenAiAsrClient` 指向本地 `HttpServer`，打印实际请求头：

```
content-type: multipart/form-data;boundary=...
transfer-encoding: chunked        ← 问题
```

3. 根因：Spring `MultipartBodyBuilder` + `RestClient` 默认流式输出，请求不带 `Content-Length`；
   SiliconFlow 对 chunked 上传直接 500。

**修复**：手写 multipart（`ByteArrayOutputStream`）+ `HttpClient.BodyPublishers.ofByteArray`，
请求自动带 `Content-Length`，与 curl 行为一致。回归测试断言「有 Content-Length、无 Transfer-Encoding」。

### 1.6 小结

v1 解决了「能不能用」，但没解决「像不像对话」。整段上传的物理延迟无法优化——只能换架构，于是有 v2。

## 2. 版本二：WebSocket 流式首发

### 2.1 设计目标

- 边说边传，不再等「停止录音」；
- 服务端按语义断句，一句一转发；
- 说完一句就能看到文字，延迟压到 1~2s。

### 2.2 整体架构

```mermaid
flowchart LR
    Mic[麦克风] --> AW[AudioWorklet]
    AW -->|Float32| Buf[主线程累积 100ms]
    Buf -->|Int16 PCM 3.2KB/帧| WS[/ws/asr]
    WS --> VAD[VadSegmenter]
    VAD -->|切出一段| Exec[线程池]
    Exec --> ASR[POST /audio/transcriptions]
    ASR -->|text| WS
    WS -->|TRANSCRIPT| UI[实时字幕/作答框]
```

### 2.3 协议（v2）

| 方向 | 消息 | 说明 |
|---|---|---|
| C→S | 二进制帧 | 16kHz / 16bit / 单声道 PCM，100ms 一帧 |
| C→S | `{"type":"STOP"}` | 请求收尾 |
| S→C | `READY` | `{sampleRate, frameMs, endSilenceMs, provider}` |
| S→C | `SPEECH_START` | VAD 判定开始说话 |
| S→C | `TRANSCRIPT` | `{text, seq, startMs, endMs, latencyMs, provider}` |
| S→C | `ERROR` / `STOPPED` | 失败 / 收尾完成 |

### 2.4 VAD 设计（v2）

`VadSegmenter`（零第三方依赖）：

```
阈值 = max(0.012, 噪声底 × 3.0)
每帧算归一化 RMS → 连续 2 帧超阈值进入语音
静音连续 6 帧（600ms）→ 切句输出
单段超过 150 帧（15s）→ 强制切段
切段时回补 2 帧（200ms）预卷
```

参数：

| 参数 | v2 值 |
|---|---|
| energy-threshold | 0.012 |
| noise-factor | 3.0 |
| min-speech-ms | 200 |
| end-silence-ms | 600 |
| max-segment-ms | 15000 |
| pre-roll-ms | 200 |
| worker-threads | 3（全局共享池） |
| queue-capacity | 4 |

### 2.5 优点

| 优点 | 说明 |
|---|---|
| 延迟数量级下降 | 从 12s 降到 ~1s（同段音频） |
| 交互自然 | 边说边出字，可即时纠错继续补充 |
| 复用现有 ASR | 不换供应商，只把「整段」切成「逐句」 |
| 资源可控 | 只有切出的语音段才调用 ASR，静音不花钱 |

### 2.6 缺点与实测缺陷

| 缺陷 | 表现 | 实测证据 |
|---|---|---|
| 小声漏检 | 说话完全没反应 | 0.06 增益档 `SPEECH_START=0` |
| 句子切碎 | 只识别出半句 | 0.2 增益档文本 `端开发经验。` |
| 尾句丢失 | 点停止也没最后一句 | 1.0 增益档 `SPEECH_START=1` 但 `段数=0` |
| 文本乱序 | 后半句先出现 | 0.06 档 `高并发交易系统。后端开发经验。` |
| 延迟暴涨 | 偶发 9s 才出字 | 0.2 档 `latency=9037ms` |

### 2.7 当时怎么发现的

1. **用户反馈**：「有时候检测不出来」「全说完点确认才翻译」；
2. **量化复现**：写 `web/scripts/vad-probe.mjs`，把同一段 8.0s 中文语音按 1.0/0.35/0.2/0.06 四档增益推给 `/ws/asr`，记录 `SPEECH_START / TRANSCRIPT / STOPPED` 事件与文本；
3. **事件顺序对比**：发现 `STOPPED` 早于 `TRANSCRIPT`，证实「尾句在连接关闭后才返回」；
4. **日志印证**：服务端 `流式转写完成 seq=... 耗时=9037ms` 说明多段并发排队；
5. **浏览器侧复现**：Playwright + 假麦克风观察 WS 帧与 UI 状态。

### 2.8 根因归纳

1. `STOP` 只提交不等待 → `STOPPED` 语义错误（「已受理」被当成「已完成」）；
2. 固定阈值 0.012 高于笔记本麦克风经降噪后的实际电平；
3. 进入与保持用同一阈值，句中断顿被当句尾；
4. 多段并发转写 → 乱序 + 排队延迟；
5. 噪声底随说话上涨形成正反馈（系数 3.0 偏激进）。

## 3. 版本三：流式修复版（当前）

### 3.1 改动总览

| 编号 | 改动 | 文件 |
|---|---|---|
| F1 | `STOP` → flush → 等在途任务归零 → 才发 `STOPPED`，并加 20s 兜底 | `StreamingAsrWebSocketHandler#stop` |
| F2 | 绝对下限 0.012 → 0.006，噪声系数 3.0 → 2.2 | `VoiceStreamProperties` |
| F3 | 迟滞：保持阈值 = 进入阈值 × 0.55 | `VadSegmenter#accept` |
| F4 | 能量 3 帧滑动平均，抑制单帧毛刺 | `VadSegmenter#smoothedLevel` |
| F5 | 每连接**单线程**有界执行器（保序 + 背压） | `newExecutor` |
| F6 | 噪声底只在非语音帧更新，平滑系数 0.08 | `VadSegmenter` |
| F7 | 新增 `SPEECH_END`、`TRANSCRIPT.final` | handler |
| F8 | 前端 `stop()` 等 `STOPPED`（12s 兜底）再汇总文本 | `useStreamingTranscription` |

### 3.2 关键设计说明

**为什么用迟滞而不是单纯调低阈值**：调低阈值会让噪声误触发；迟滞把「进入」与「保持」分开，进入仍需明确能量，保持允许弱读，这是语音产品的通行做法。

**为什么每连接单线程**：同一场对话的分段本就有先后，并发只会乱序；单线程 + 有界队列既保序又有背压，代价是极端情况下排队（可接受）。

**为什么 STOPPED 要等**：客户端收到 STOPPED 就会关闭连接并汇总文本，这是唯一的「结果全部推送完毕」信号；早发就会丢尾句。

### 3.3 参数（v3）

| 参数 | v3 值 | 调大/调小的效果 |
|---|---|---|
| energy-threshold | 0.006 | 调小更灵敏、更易被噪声触发 |
| noise-factor | 2.2 | 调小更灵敏、嘈杂环境更易误触发 |
| end-threshold-ratio | 0.55 | 调大更严格（易切句），调小更连贯（易粘句） |
| smooth-frames | 3 | 调大更平滑、响应更慢 |
| min-speech-ms | 160 | 调大过滤短噪声，但短促回答可能被丢 |
| end-silence-ms | 600 | **主要延迟旋钮**：400 更快但易切碎，800 更稳但更慢 |
| max-segment-ms | 15000 | 长句强制切段上限 |
| pre-roll-ms | 240 | 回补首字，调大更安全但会增加段长 |
| worker-threads | 4 | 全局池（当前用于兜底），实际每连接 1 线程 |
| queue-capacity | 8 | 背压上限，满了丢最旧 |
| stop-timeout-ms | 20000 | 收尾兜底 |

### 3.4 修复前后对比（同一 8.0s 音频，四档增益）

| 增益 | v2 结果 | v3 结果 | v3 延迟 |
|---|---|---|---|
| 1.00 | 0 段（尾句丢失） | 1 段，完整 | 843ms |
| 0.35 | 0 段 | 1 段，完整 | 362ms |
| 0.20 | 1 段，`端开发经验。` | 1 段，完整 | 352ms |
| 0.06 | 0 段（漏检） | 2 段，均识别 | 258ms |

事件顺序：v2 `SPEECH_START → STOPPED`；v3 `SPEECH_START → SPEECH_END → TRANSCRIPT → STOPPED`。

### 3.5 优点

- 延迟 0.26~0.85s，接近「说完就出字」；
- 小声、句中断顿、尾句、乱序四类实测缺陷全部覆盖；
- 保留完整降级链：流式失败 → 整段上传 → 文字作答。

### 3.6 剩余风险

| 风险 | 说明 | 建议 |
|---|---|---|
| 噪声环境误触发 | 能量 VAD 的固有局限 | 换 Silero/WebRTC VAD |
| 极低音量仍会截断 | 0.06 增益下首句被切成两段 | 服务端加 AGC 后再送 ASR |
| 方言/口音 | SenseVoice 对部分方言一般 | 可换 Paraformer / 专用模型 |
| 多实例 | 房间与连接状态在内存 | 粘性会话或 Redis 广播 |
| 长句截断 | 15s 强制切段 | 按标点二次切分 |

## 4. 三个 WebSocket 端点对照

项目里共有 3 个 WS 端点，分别服务不同阶段，设计取向不同：

| 端点 | 用途 | 鉴权 | 消息模型 | 版本 |
|---|---|---|---|---|
| `/ws/interview` | 招聘面试房间的实时状态（旧引擎保留） | query `token` + `interviewId`，校验归属 | 文本 JSON 事件（状态变更/题目推送） | v1 |
| `/ws/call` | 视频面试信令与 AI 字幕 | query `token` + `code` + `name` | JSON 信令（OFFER/ANSWER/ICE/AI_SAY/CHAT）+ 内存房间注册表 | v2 |
| `/ws/asr` | 流式语音转写 | query `token` + `language` | **二进制音频帧** + JSON 控制/结果 | v3 |

设计差异的原因：

- **面试房间**是「业务事件流」，只需要文本；
- **视频信令**是「点对点转发」，需要房间成员与超员控制，媒体走 WebRTC；
- **语音转写**是「高频小包 + 有序结果」，必须二进制帧、必须保序、必须有收尾语义。

共同约定：

- 都用 `HandshakeInterceptor` 做 JWT 校验（浏览器 WS 不能自定义头，只能 query）；
- 都在 `SecurityConfig` 放行 `/ws/**`，由握手拦截器负责鉴权；
- 失败时握手返回 401/404，不建立连接；
- 生产必须 `wss://`，注意访问日志脱敏（token 在 URL）。

## 5. 问题定位方法论（可复用）

| 手段 | 用在哪 | 产出 |
|---|---|---|
| **对照实验** | v1 chunked 问题：curl -F 成功 vs 客户端失败 | 锁定「传输方式」而非「文件/Key」 |
| **本地抓包** | `HttpServer` + 测试类打印请求头 | 看到 `Transfer-Encoding: chunked` |
| **多档位压测脚本** | v2 漏检：同一音频 4 档增益 | 得到「哪个音量失效」的边界 |
| **事件顺序断言** | v2 尾句丢失：记录事件时序 | 证明 `STOPPED` 早于 `TRANSCRIPT` |
| **日志耗时字段** | v2 延迟 9s：`耗时=9037ms` | 区分「ASR 慢」与「排队慢」 |
| **浏览器端复现** | 假麦克风 + Playwright | 确认前端行为与 WS 帧 |
| **单元级回归** | v3 三个回归用例 | 防止参数调整导致复发 |

核心经验：**先量数据，再改参数**。语音问题最怕「凭感觉调阈值」。

| BUG-01-b | 语音 | 严重 | 小声说话完全无反应 | 固定阈值 0.012 高于实际电平 | 已修复（F2） |
| BUG-01-c | 语音 | 中 | 句子被切成半句 | 无迟滞，句中断顿当句尾 | 已修复（F3/F4） |

| BUG-02 | 语音 | 高 | ASR 上传 500 | chunked multipart 被拒 | 已修复（手写 multipart） |
| BUG-03 | 出题 | 中 | 无简历仍出简历题 | 历史题干含简历信息被喂给模型 | 已修复 |

### 6.9 覆盖缺口（明确未测/未验证）

| 项 | 现状 | 风险 |
|---|---|---|
| 多实例部署下的 WS | 未测（状态在内存） | 需要粘性会话/Redis 广播 |
| TURN / 跨 NAT | 未测（只有 STUN） | 严格 NAT 下无法连通 |
| 扫描件 PDF | 明确不支持（提示粘贴） | 用户需自行转文本 |
| 豆包 TTS 真实音质 | 未验证（无凭证） | 需要用户提供 appid/token |
| 移动端语音 | 未在真机验证 | iOS Safari 的 AudioWorklet 兼容性需实测 |
| 高并发 | 未做压力测试 | 单机房间数与连接数上限未知 |

## 7. 如果继续迭代，建议顺序

1. **AGC + 更强 VAD**（Silero）→ 解决噪声与极低音量；
2. **TURN 与多实例信令** → 让视频真正可对外使用；
3. **题库扩容 + 简历题库化** → 提升无简历时的题目质量；
4. **豆包 TTS 实测** → 音质从「机械」到「自然」；
5. **CI 化**：把 4 个 E2E 脚本接进流水线，语音链路加指标看板（首字延迟、检出率、错误率）。
