# 缺陷报告 01：流式语音转写漏检与尾句丢失

> 报告编号：BUG-01
> 模块：语音（`ai/voice/stream`）、视频面试与练习房间的语音作答
> 发现时间：2026-11-27
> 修复版本：`9344453` 之后
> 状态：已修复，已补回归测试

---

## 1. 现象（用户反馈）

1. 说话时**有时候完全没反应**，界面上不出现任何转写文字；
2. 有时说完一句话后**必须点「停止录音」才出字**，甚至点了也**没有最后一句**；
3. 偶尔出现**语句顺序错乱或截断**，例如只说出了「端开发经验。」。

---

## 2. 复现环境与手段

- 后端：本地 jar（硅基流动 `FunAudioLLM/SenseVoiceSmall` 转写）
- 复现脚本：`web/scripts/vad-probe.mjs`
  - 用系统语音合成生成 8.0s 中文语音；
  - 重采样到 16kHz、按 100ms 一帧推给 `/ws/asr`；
  - 以不同音量增益（1.0 / 0.35 / 0.2 / 0.06）分别复现；
  - 记录 `SPEECH_START` / `SPEECH_END` / `TRANSCRIPT` / `STOPPED` 事件顺序与文本。
- 语音帧 RMS 分布（8.0s，原始音量）：中位数 0.0303，p20 0.0001，p80 0.1017，最大 0.2713。
- 浏览器侧另用 Playwright + Chrome 假麦克风复现，观察 WS 帧与 UI。

## 3. 实测数据（修复前）

| 增益 | 等效音量 | SPEECH_START | 段数 | 转写文本 | 首段延迟 |
|---|---|---|---|---|---|
| 1.00 | 正常 | 1 | **0** | 空 | — |

---

## 4. 根本原因

### 4.1 尾句丢失：`STOP` 只提交不同步（严重）

修复前 `handleTextMessage` 收到 `STOP` 后：

```java
for (Segment s : segmenter.flush()) submit(session, s);
send(session, Map.of("type", "STOPPED"));   // 立刻回
```

前端收到 `STOPPED` 就断开连接并读取文本，而最后一段的转写还在线程池里执行，
结果回来时连接已关闭 → **永远拿不到最后一句**。这正是「说完了点确认也没字」的原因。

### 4.2 漏检：固定能量阈值过高

修复前阈值固定为 `max(0.012, 噪声底 × 3.0)`。
笔记本麦克风经浏览器 `echoCancellation` / `noiseSuppression` 处理后，正常说话 RMS 常在
0.01~0.02；安静或离麦远时更低。**低于 0.012 就完全不会触发 VAD**，与实测 0.06 增益档
（RMS≈0.0018）一致。

### 4.3 句子被切碎：缺少迟滞（hysteresis）

修复前判定「仍在说话」用的是同一个进入阈值。句中换气、弱读音节能量常降到峰值 40%~50%，
一旦低于阈值就累计静音帧，600ms 后切句，导致转写只覆盖半句（`端开发经验。`）。

### 4.4 文本乱序：多段并发转写

线程池 3 线程，连续两段几乎同时结束时，后一段可能先返回，前端按到达顺序拼接 →
出现「高并发交易系统。后端开发经验。」这种倒序。

### 4.5 延迟暴涨：排队

同一段音频被切成多段并发提交，ASR 服务被并发占用，单段延迟从 ~1s 涨到 **9s**，
用户感知就是「很慢」。

### 4.6 噪声底被说话声污染（次要）

修复前只在 `level <= threshold` 时更新噪声底，看似正确；但阈值本身随噪声底上涨，
配合 3.0 系数形成正反馈，在嘈杂环境里越用越迟钝。

---

## 5. 修复方案

| 编号 | 修复 | 位置 |
|---|---|---|
| F1 | `STOP` 改为「flush → 统计在途任务 → 全部完成后再发 `STOPPED`」，并加 `stop-timeout-ms` 兜底 | `StreamingAsrWebSocketHandler#stop` |
| F2 | 绝对下限降到 `0.006`，噪声系数降到 `2.2` | `VoiceStreamProperties` |
| F3 | 引入迟滞：进入阈值 `T`，保持阈值 `T × end-threshold-ratio(0.55)` | `VadSegmenter#accept` |
| F4 | 能量做 3 帧滑动平均，抑制单帧毛刺 | `VadSegmenter#smoothedLevel` |
| F5 | 每连接一个**单线程有界执行器**，保证分段按 seq 顺序转写 | `StreamingAsrWebSocketHandler#newExecutor` |
| F6 | 噪声底只在非语音帧更新，并降低平滑系数到 0.08 | `VadSegmenter#accept` |
| F7 | 前端 `stop()` 等 `STOPPED`（12s 兜底）再断开并汇总文本 | `useStreamingTranscription.stop` |
| F8 | 新增 `SPEECH_END` 消息、`TRANSCRIPT.final` 标记，UI 可区分是否收尾 | handler |

## 8. 经验沉淀（后续同类改动的固定动作）

1. **先量数据再改参数**：用合成音频按增益档位测，而不是凭感觉调阈值；
2. **异步链路必须有「完成信号」语义**：`STOPPED` 代表「所有结果已推送」，不能代表「已受理」；
3. **并发要按业务顺序约束**：同一场对话的分段必须串行，牺牲一点吞吐换正确性；
4. **VAD 这类信号处理要有迟滞**：进入与保持用不同阈值，是所有语音产品的通行做法；
5. **每个缺陷都要留回归用例**：本次 3 个用例直接命名对应现象，防止后续「优化参数」时复发。

## 9. 遗留与改进方向

| 项 | 说明 |
|---|---|
| 噪声环境下的鲁棒性 | 当前为能量 VAD，嘈杂环境仍可能误触发；可换 WebRTC VAD / Silero VAD（需引入模型或原生库） |
| 方言与低音量 | 可加自动增益（AGC），在服务端对每段做归一化后再送 ASR |
| 首字延迟 | `pre-roll-ms=240` 已缓解；如需更激进可让前端在 `SPEECH_START` 时预发整段音频 |
| 断句稳定性 | 长句强制切段（15s）会产生截断，可考虑按语义标点二次切分 |
